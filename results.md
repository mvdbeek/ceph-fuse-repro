# Results

Reproducer for the js2-2xl9 ceph-fuse stall: buffered reads of a file written by another client hang in `fuse_get_req`, while O_DIRECT, stat and own writes work.

Raw data lives in `results/<run>/` (`run.json`, `summary.json`, `events.jsonl`, `fusectl.tsv`, role logs, capture bundles, `NOTE` where a run needed explanation) and in `results/runs.tsv`. The tables at the end are generated by `harness/report.py`.

## Summary

- **An environmental cause reproduces the full production signature with no client bug** (Finding 6). A path-MTU black hole between the node and *one* OSD:
  - buffered reads of fresh files hang in `fuse_get_req`;
  - `stat`, own writes and O_DIRECT reads of files on other OSDs work;
  - `ceph health` stays HEALTH_OK;
  - the state persists until the path is fixed.

  A client bug and a node-local network/OSD-path fault look identical from the probes that were run in production. `objecter_requests` on the ceph-fuse admin socket tells them apart; see [What to check on a stuck node](#what-to-check-on-a-stuck-node).
- **No spontaneous reproduction.** The valid negative runs and their durations are in [Run totals](#run-totals). Production saw about 1 event per 34 days of node uptime.
- **H1's mechanism gives exactly the production signature on the production kernel** (Finding 1). This ceph-fuse build uses libfuse 2, so O_DIRECT reads are synchronous FUSE requests and bypass the `max_background` gate, while readahead waits on it. H1 still needs requests that ceph-fuse never answers.
- **The production `fn_anonymous` hung-task stack was reproduced on 6.1.188, with identical offsets** (Finding 2). It lasted about 15 min and then recovered, as in production. The trigger was a 6 s cluster-FULL episode caused by the harness, not a spontaneous one.
- **A ceph-fuse ObjectCacher bug loses reads permanently, and it reproduces the full production signature on demand** (Findings 3 and 7). A discard that hits a buffer with a read in flight, followed by a cache trim before the OSD reply, deletes the reader's waiter. With 12 lost reads, the 6.1.188 guest shows:
  - buffered reads hang in `fuse_get_req`;
  - `stat`, O_DIRECT and writes work;
  - no OSD/MDS ops are outstanding and the cluster is HEALTH_OK;
  - the production `fn_anonymous` hung-task stack, permanently.

  The reproducer triggers the discard with a same-client `fallocate` punch hole; truncate is protected by caps. Whether anything on js2-2xl9 punches holes, or reaches the discard another way, is not known. The bug is unchanged on ceph `main` and worth reporting upstream.
- **A small fix in `ObjectCacher::Object::discard` closes it** (Finding 8): restart the waiters of an rx buffer when it is discarded. A new unit test fails on 17.2.9 and passes with the fix. With a patched ceph-fuse, the reproducer's reads all complete (3 of 3 single-file runs and 12 of 12 reads in the 12-file run), although the race fired in every case; the packaged ceph-fuse still hangs in the same session. Patches for 17.2.9 and ceph `main` are in `patches/`.
- **ceph-fuse 17.2.9 segfaults on the admin-socket command `log dump`** (Finding 4). After that crash, a blocked invalidation hung the mount until `fusectl abort` released it.
- **Brief cluster-FULL episodes don't reliably trigger the stall**: 0 stalls in about 11 flaps on 6.1.188 and 2 on 7.3 (Finding 5).
- **The campaign was stopped by decision**: low odds of a spontaneous hit at this rate, and the environmental hypothesis is now testable on the real node.

## Finding 1: exhausted FUSE background slots give the production signature

`harness/h1_mechanics.sh` fills the node's background-request slots on purpose. It pauses the OSDs so that the readahead of about 29 buffered readers sits inside ceph-fuse, then probes. Logs: `results/h1-mechanics-kernel6.1.188/`, `results/h1-mechanics-kernel7.3/`.

With the slots full on 6.1.188 (`waiting=17`, `max_background=12`):

| Probe on node | Result |
|---|---|
| `stat` | ok |
| buffered read of a file ceph-fuse has cached (page cache dropped) | **hangs in D, `wchan=fuse_get_req`**: the production cp/md5sum signature |
| O_DIRECT read of the same file | passes the gate: a synchronous FUSE READ goes to ceph-fuse (`request_wait_answer`; ceph-fuse logs `_read_sync`) |
| after the OSDs return | `waiting=0`, everything works |

Kernel 7.3 gives the same result.

Why O_DIRECT bypasses the gate: the kernel only sends O_DIRECT reads as background requests when `FUSE_ASYNC_DIO` was negotiated. libfuse 2.9.9 doesn't know that flag. So with this ceph-fuse build, the production split is just what H1 predicts: buffered reads hang, O_DIRECT works.

**What would confirm H1 on a stuck production node:** `cat /sys/fs/fuse/connections/*/waiting` at or above 12 while idle, with `objecter_requests` and `mds_requests` on the ceph-fuse admin socket empty. Until then, `echo 1 > /sys/fs/fuse/connections/<id>/abort` releases everything. Raising `max_background` there would let new background requests through.

## Finding 2: the production invalidation hang, identical stack, on the production kernel

Run `20261106-182048-B-baseline` (Stage B, no faults; see its `NOTE`). This happened after 30 minutes of the workload:

```
fn_anonymous  D  (ceph-fuse Finisher thread), syscall writev on /dev/fuse
folio_wait_bit_common+0x120/0x360
invalidate_inode_pages2_range+0x12f/0x380
fuse_reverse_inval_inode+0x93/0xc0 [fuse]
fuse_notify+0x3b6/0x520 [fuse]
fuse_dev_do_write+0x305/0x4e0 [fuse]
fuse_dev_write+0x50/0x80 [fuse]
do_iter_readv_writev / do_iter_write / vfs_writev / do_writev
```

- These are the same frames and offsets as the 2026-10-03 production report. The guest kernel printed its own hung-task reports every ~123 s, up to "blocked for more than 860 seconds" (`live-stuck/guest-console.log`).
- Node readers were stuck in `filemap_update_page` / `filemap_fault` → `folio_wait_bit_common`, waiting for page locks held by in-flight reads. `kcompactd0` was stuck as well.
- `fusectl waiting` was 5, so the slots were not exhausted.
- **ceph-fuse had no OSD and no MDS request outstanding.**
- It **recovered by itself after about 14.5–16.5 min**, as production's "thread later recovered".

**Not spontaneous.** It started 16 s after the cluster went `OSD_FULL` for 6 s (17:50:14–17:50:20 UTC). The harness's 8 GB OSDs had filled up. ceph-fuse handles FULL in `_handle_full_flag` by cancelling outstanding writes with ENOSPC and purging dirty data. The stall then outlasted the FULL episode by about 15 minutes. The post-recovery state was lost: gdb, loading full debuginfo, wedged the guest. A 3.2 GB guest memory dump was kept locally (not committed).

An earlier Stage A control showed the same `fn_anonymous` state, from syscall plus wchan, during a hand-made 100 s OSD pause, and it recovered when the OSDs returned.

## Finding 3: source review (ceph-fuse 17.2.9, kernel 6.1.188 FUSE, libfuse 2.9.9)

Two read-only reviews of the source. Their key code claims were re-checked.

**Kernel FUSE (6.1.188): no leak or deadlock found.**

- The invalidation waits on `PG_locked`, and so do the readers.
- `num_background` is decremented only in `fuse_request_end`, and every path reaches it: reply, abort, or device release.
- Exclusive wake-ups are passed on correctly.
- The reverse-invalidate notify holds only `killsb` (read). It doesn't stop other server threads from replying.
- So every stall needs a FUSE request that ceph-fuse has not answered. A 15-minute recovery has to come from the ceph side, since kernel 6.1 has no request timeout.

**libfuse 2.9.9.**

- It negotiates ASYNC_READ but neither ASYNC_DIO nor WRITEBACK_CACHE, and `max_background` stays at the kernel default.
- The kernel rejects reply errors ≤ −512 before matching the request, which would leak a slot. ceph-fuse can't produce one: `get_sys_errno` maps everything to at most 131, or to EIO.

**ceph-fuse 17.2.9.**

- The invalidate callback runs on its own Finisher. Nothing in ceph-fuse waits for it, so a blocked invalidation is a symptom, not the cause.
- A READ can block with no OSD or MDS op outstanding in `get_caps`, while waiting for Fr or for an Fc revoke to finish. That wait ends only when a cap message arrives.
- **Permanent lost read (from code, checked line by line; since reproduced, see Finding 7):**
  1. `Object::discard` (`ObjectCacher.cc:644-651`) turns an `rx` buffer, one with a read in flight, into `zero`. It keeps its `waitfor_read`, and the state change unpins it from the LRU (`set_state` → `put()` → `lru_unpin()`).
  2. `trim()` (`:1322-1331`) deletes clean or zero buffers without completing `waitfor_read`.
  3. When the OSD reply arrives, `bh_read_finish` only completes waiters on buffers still in `ob->data`.
  4. If trim ran first, the waiting `_read_async` never returns. The FUSE READ is never answered, its background slot leaks for good, and its page stays locked. O_DIRECT, which bypasses the ObjectCacher, keeps working.

  The trigger path: node sees a truncate (`update_inode_file_size` → `_invalidate_inode_cache` → `discard_writeback`) while its readahead on that range is in flight. That same call also schedules the kernel invalidate run by `fn_anonymous`. This code is unchanged in reef, squid and main.
- **Why the race is hard to hit:** readahead holds Fr|Fc cap references until it completes. So the MDS can't finish revoking node's caps for another client's truncate while the read is in flight. In a 60 s `debug_objectcacher=10` sample of the targeted run, there were 5 discards and none of them hit an `rx` buffer.

## Finding 4: `log dump` segfaults ceph-fuse 17.2.9; a blocked invalidation then hangs the crash

Run `20261106-202935-A-octrim-truncate` (see its `NOTE`).

- The capture's `ceph --admin-daemon ... log dump` crashed ceph-fuse in `ceph::logging::Log::dump_recent()` → `pthread_getname_np()`. The ring holds entries from libfuse worker threads that have already exited.
- One `fn_anonymous` was blocked in the invalidation, so the core dump could not finish (`admin_socket` in D in `vfs_coredump`). ceph-fuse never exited, and the mount hung instead of returning ENOTCONN. `stat` of the mount root sat in `request_wait_answer` for more than 19 min.
- `echo 1 > /sys/fs/fuse/connections/<id>/abort` released it at once.

`log dump` was removed from the capture.

## Finding 6: a black hole to one OSD gives the production signature, with the cluster healthy

`harness/blackhole.sh`; log in `results/blackhole-osd0-kernel6.1.188/`.

Setup:
- Head writes 40 fresh 4 MB files; 8 of them have osd.0 as primary.
- On osd.0's interface, a tc filter drops packets larger than 1400 bytes addressed to the node (Stage B guest, kernel 6.1.188). Requests and acks still get through, so TCP keeps retransmitting instead of failing.
- The node buffered-reads all 40 files.

Results:

| On node | After 60 s | After 5 min |
|---|---|---|
| fusectl `waiting` (`max_background=12`) | 47 | 52 |
| readers | 35 in D `fuse_get_req`, 5 in D `folio_wait_bit_common` | same |
| ceph-fuse `objecter_requests` | 12 ops, **all to osd.0**, oldest 62 s | 13 ops, all to osd.0, oldest 357 s |
| buffered read of a fresh file (any OSD) | **hangs, D `fuse_get_req`** | hangs |
| `stat`; write + read own file | ok | |
| O_DIRECT read, file on a healthy OSD | ok | |
| O_DIRECT read, file on osd.0 | hangs (`request_wait_answer`) | |
| `ceph health` | | **HEALTH_OK** |

After the filter was removed, everything recovered within 97 s (`waiting=0`, all readers done).

This matches every production probe:
- the hanging `cp` and `md5sum`;
- working `ls`, write-then-read and O_DIRECT of a fresh 1 MB file, which most likely lived on a healthy OSD;
- a cluster that looked fine.

With a persistent path fault, each reconnect resends the same ops into the same black hole, so a stall lasting days is plausible. Not tested here beyond 5 minutes.

Production also had one observation that neither hypothesis explains: buffered reads of `registry.xml` worked after the `cp` was killed.

The fault could be anything that silently loses large packets or replies on that path:
- an MTU mismatch on one hypervisor or one switch port;
- a flaky NIC or virtio queue;
- a stuck conntrack or security-group state;
- a problem on one OSD host.

## Finding 7: the ObjectCacher lost read is real, and reproduces the whole production signature on demand

`harness/oc_lostread.sh` drives the Finding 3 path step by step on the node client:

1. Hold all replies from osd.1 to the node (tc drop on osd.1's egress, filtered on the node's IP).
2. Start buffered reads of N files whose only object is on osd.1, so their buffers sit in `rx`.
3. From the **same client**, punch a hole over each file (`fallocate -p`). `Client::_fallocate` calls `_invalidate_inode_cache(in, off, len)` → `discard_writeback` directly, with no MDS round trip.
4. Make `trim()` run, using either:
   - `churn`: buffered reads of other files through a 2 MiB `client_oc_size`;
   - `wchurn`: one committed write, then a write with a 4 KiB cache. This variant is needed once the background slots are full.
5. Release the replies.

The client log shows the predicted chain every time. From the first run:

```
17:56:00.429 bh_read on bh[0x786df4028460 0~131072 missing]; readx missed, waiting on bh[... rx]
17:56:04.720 discard ... bh bh[0x786df4028460 0~131072 ... rx] waiters = { 0->[0x786df40240f0, ]}
17:56:08.850 trim trimming bh[0x786df4028460 0~131072 ... zero] waiters = { 0->[0x786df40240f0, ]}
17:56:13.378 bh_read_finish 1000000080c.00000000/head tid 115 0~131072 returned 0      <- no buffer left; nobody is woken
```

| variant | runs | discard hit rx with waiter | zero buffer trimmed with waiter | outcome |
|---|---|---|---|---|
| punch + churn, 1 file (A, 7.3) | 5 | 5/5 | 5/5 | **5/5 read never returns** |
| punch, no churn (A) | 1 | 1 | 0 | read completes when replies are released (waiters kept on the zero buffer) |
| no discard + churn (A) | 2 | 0 | 0 | read completes |
| truncate + churn (A) | 2 | 0 | 0 | read completes; see below |
| punch + wchurn, 12 files, 1 MiB cache (A) | 1 | 8 | 8 | 8/12 lost: the 1 MiB cache held back 4 reads (`waiting on cache to complete`), an artifact of the tiny cache |
| punch + wchurn, 12 files (A, 7.3) | 1 | 12 | 12 | **12/12 lost, production signature** |
| punch + wchurn, 12 files (**B, 6.1.188**) | 1 | 12 | 12 | **12/12 lost, production signature and hung-task stack** |

Two further runs are invalid, both harness stalls in the churn step (each has a `NOTE` in its directory). Every punch + churn run lost the read. The race is deterministic once its preconditions are set up. Each run takes about 2 minutes, most of it the 60 s wait after release.

**With 12 lost reads, the node looks like js2-2xl9** (Stage B, `results/oclost-B-punch-wchurn-n12-*`):
- fusectl `waiting` = 14 with `max_background` = 12, no objecter ops outstanding, HEALTH_OK;
- `stat`: ok; O_DIRECT read: ok; write: ok;
- **buffered read of an uncached file: hangs, wchan `fuse_get_req`**;
- another client reading the same file hangs, because node leaked the `FILE_CACHE` cap ref held by the lost read and can never release its caps;
- the kernel hung-task report is the production one, frame for frame:

```
INFO: task fn_anonymous:5346 blocked for more than 122 seconds.
 folio_wait_bit_common+0x120/0x360
 invalidate_inode_pages2_range+0x12f/0x380
 fuse_reverse_inval_inode+0x93/0xc0 [fuse]
 fuse_notify+0x3b6/0x520 [fuse]
 fuse_dev_do_write+0x305/0x4e0 [fuse]
```

This is permanent, unlike the self-healing stall of Finding 2. The invalidate scheduled by the discard waits on the page that the lost read keeps locked.

**Killing ceph-fuse does not free the mount.** The `fn_anonymous` thread is in an uninterruptible kernel wait, so the process stays a zombie with `/dev/fuse` open. Only `echo 1 > /sys/fs/fuse/connections/<id>/abort` releases it.

**Which discards can hit an in-flight read.** `Object::discard` is reached from two places in `Client.cc`:
- **truncate** (`update_inode_file_size` → `_invalidate_inode_cache`, about line 911). The cap protocol protects this path. The MDS revokes `Fr` before applying a truncate, and the client delays that revoke while the read holds its `FILE_RD` reference. In both truncate runs, the reply (14.947) arrived before the discard (14.950). This applies to truncates from the same client or another one.
- **fallocate punch hole** (`_fallocate`, about line 15107). This path needs only `Fw`/`Fb`, which the reading client can hold at the same time as `Fr`/`Fc`. Nothing orders it against an in-flight read on the same client.

Same-client writes over an rx buffer keep the waiters (`map_write` marks the buffer dirty, and `merge_left` moves waiters). The write also goes to the same object, so the OSD orders it after the read. That path did not look exploitable and was not tested.

**What this means for production:**
- The mechanism fully explains the production signature: `fuse_get_req`, working O_DIRECT, `stat` and writes, the `fn_anonymous` stack, and a quiet cluster.
- The **trigger used here (punch-hole on a file the same node is reading) is not known to happen on js2-2xl9**. Candidate sources are anything on the node that calls `fallocate(PUNCH_HOLE)`, e.g. `cp --sparse=always`, `fallocate --dig-holes`, or tools and libraries that punch holes.
- There may be another discard source this review missed. The production cache is 200 MB, so trim also needs cache pressure before the reply arrives. A slow OSD reply widens that window.
- It is now worth tracing on the node. See [What to check on a stuck node](#what-to-check-on-a-stuck-node).

**Reportable upstream.** The code is unchanged on ceph `main`: the same rx branch in `Object::discard` and an identical `trim()`. The reproducer is deterministic and needs no special build. One possible fix: `discard` should not unpin an rx buffer that still has waiters. Alternatively, `trim()` and `release()` could complete (retry) `waitfor_read` before deleting a buffer, as `discard` does for non-rx buffers.

## Finding 8: the fix, with a unit test and the reproducer

**Fix** (`patches/0002-…`, and `patches/upstream-main/0001-…` for ceph `main`). In `ObjectCacher::Object::discard`, the rx branch now moves the buffer's `waitfor_read` contexts to the list that `discard` already restarts for buffers in every other state:

```cpp
      oc->mark_zero(bh);
      // a zero bh is not pinned, so trim() or release() may delete it
      // before the read reply arrives, and bh_read_finish() could then not
      // find the waiters. restart them now; they will see the zeroed range.
      for ([[maybe_unused]] auto& [off, ctxs] : bh->waitfor_read) {
        waiting_for_read.splice(waiting_for_read.end(), ctxs);
      }
      bh->waitfor_read.clear();
```

- **Why this is safe.** The retried `_readx` finds the zero buffer and returns zeros, which is the correct content of a discarded range.
- **The late OSD reply** is still ignored: `discard` already bumps `last_read_tid`, so the reply cannot overwrite the discard.
- **Same path as before.** Restarting from inside `discard`, with the cache lock held, is what `discard` already does for non-rx buffers.

**Unit test** (`patches/0001-…`): `unittest_object_cacher`, a gtest built against `osdc`. A `WritebackHandler` holds every read until the test answers it, so the order is exact:

| Test | Sequence | 17.2.9 | With the fix |
|---|---|---|---|
| `DiscardInFlightReadThenTrim` | read (held), `discard_set`, hit on another object that makes `_readx` call `trim()`, reply | FAILED: read never completes | OK, zeros |
| `DiscardInFlightReadThenRelease` | read (held), `discard_set`, `release_set`, reply | FAILED: read never completes | OK, zeros |
| `DiscardInFlightRead` | read (held), `discard_set`, reply (nothing deletes the buffer) | OK | OK, zeros |

The third test passes before the fix because `bh_read_finish` collects waiters from any buffer still in the object. That is why the bug needs the trim or release between the discard and the reply.

**Reproducer** (`scripts/build-ceph-fuse.sh`, then `CFR_PATCHED=1`). The build is ceph-fuse 17.2.9 from the release tarball, built on Rocky 9 with gcc 11 like the el9 packages, and run with its own `libceph-common` (and `libfmt`) through `LD_LIBRARY_PATH`. Stage A, same cluster, back to back:

| Run | ceph-fuse | rx discards with waiters | trims of the zeroed buffer | Outcome |
|---|---|---|---|---|
| `oclost-patched-20261108-154341-punch-churn-1-r1..r3` | patched | 1, 1, 1 | 1, 1, 1 (`waiters = {}`) | all reads complete (3 of 3) |
| `oclost-patched-20261108-154341-punch-wchurn-12` | patched | 12 | 12 (`waiters = {}`) | 12 of 12 reads complete |
| `oclost-packaged-20261108-154640-punch-churn-1` | packaged | 1 | 1 (waiter still attached) | READ HUNG |

- **Timing.** With the fix, the read is answered at the moment of the discard, while the OSD replies are still held. The log shows `restarting reads post-discard`, then `readx hit … zero`, then `result is 131072`. The punch hole's own OSD op waits for the release, as it should.
- **Not run:**
  - Stage B with the patched binary. The fix is in user space, and Stage A already gives the full lost-read signature without it.
  - The `main` patches were not compiled. `ObjectCacher`, `WritebackHandler` and the test helpers they use have the same API on `main` as on 17.2.9, where both patches were built and tested.

**Upstream.** The `main` patches are signed off and pushed to https://github.com/mvdbeek/ceph/tree/wip-objectcacher-discard-rx. A draft tracker issue is in `patches/upstream-main/tracker-issue.md`. Once the issue exists, add `Fixes: https://tracker.ceph.com/issues/<id>` to the fix commit before opening the PR.

## What to check on a stuck node

All of these are read-only and work without a reboot:

```sh
cat /sys/fs/fuse/connections/*/waiting          # >= 12 while idle: background slots exhausted (needs root)
ceph daemon /var/run/ceph/ceph-client.<id>.asok objecter_requests   # see below
ceph daemon /var/run/ceph/ceph-client.<id>.asok mds_requests
ss -tnoi | grep -A1 ':68[0-9][0-9]'              # OSD connections: Send-Q stuck, retrans rising?
ping -M do -s $((MTU-28)) <each OSD host>        # path MTU
dmesg -T | grep -iE 'blocked for more|virtio|eth|link|tx timeout'
```

How to read the result:

| `waiting` | `objecter_requests` | Interpretation |
|---|---|---|
| ≥ 12 | **old ops, mostly to one OSD** | network or OSD-path fault (Finding 6). Check that OSD host and the path to it (MTU, NIC, conntrack). |
| ≥ 12 | **empty**, and `mds_requests` empty | requests that ceph-fuse never answered: a client bug (H1, e.g. the Finding 3 lost read). Grab `gdb`/`eu-stack` thread stacks of ceph-fuse and a `dump_cache` before restarting it. |

If it is the client-bug row, also check whether something on the node punches holes (Finding 7). Either of these, run before the next stall, records the caller:
- `bpftrace -e 'tracepoint:syscalls:sys_enter_fallocate /args->mode & 2/ { printf("%s %d\n", comm, pid); }'`
- `auditctl -a always,exit -F arch=b64 -S fallocate`

The ceph-fuse log at `debug_client=3` also records `ll_fallocate`.

Escape hatches:
- `echo 1 > /sys/fs/fuse/connections/<id>/abort` kills the mount without a reboot. Killing ceph-fuse alone is not enough: with a blocked invalidation it stays a zombie holding `/dev/fuse`.
- `fuse_disable_pagecache=true` avoids the background-request path entirely, at a performance cost.

Add `kernel.hung_task_warnings=-1` and alerting on `waiting` to node monitoring.

## Harness artifacts found on the way (not ceph bugs)

- **OOM kills of ceph-fuse and the OSDs at tight container caps.** With the default 200 MB object cacher, ceph-fuse alone reaches about 400 MB RSS. After an OSD pause or a FULL flap, OSDs hold most of their memory outside Ceph's mempools. Clients now get 1.4 GB and OSDs 2.5 GB, and any OOM kill makes a run INVALID. Per-run peaks are in `summary.json`.
- **8 GB OSDs filled up during long runs.** Now 40 GB each, and old trees are deleted between runs.
- **`tc netem` jitter** reorders packets and collapses TCP throughput, so the default is a fixed delay.
- **SIGBUS for mmap readers of files another client extends.** When ceph-fuse returns a short READ, the kernel shrinks `i_size` (`fuse_short_read`), and a mapped page beyond it faults. These reads run in a child process and are counted (`node_hot_mmap_sigbus`).
- **Detector fixes:**
  - The probe check no longer depends on head being able to write.
  - It no longer blocks on a probe child that survives SIGKILL; it reports `unkillable_probe` with the kernel stack.
  - Hung-task lines from before a run are ignored.
  - The idle-leak check ignores the background cleanup.
  - Captures run in the background.
- **Timeouts to stay under:** `osd_op_thread_suicide_timeout` is 150 s, so hand-made OSD pauses should stay shorter. The guest's hung-task checker only reports blocks longer than one 120 s interval.

## Environment notes

- chonk runs rootless docker. Root granted `setfacl -m u:babysit:rw /dev/kvm` (lost once, when `/dev/kvm` was recreated) and `sysctl kernel.dmesg_restrict=0 kernel.hung_task_warnings=-1`.
- Stage A reads FUSE counters from the host's fusectl. It cannot get `/proc/<pid>/stack` or sysrq; Stage B can.
